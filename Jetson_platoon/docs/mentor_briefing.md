# 플래툰 군집주행 알고리즘 개발 현황

작성일: 2026-07-31
담당: 상위 연산부(Raspberry Pi 5) — 플래툰 알고리즘 및 주행 제어

---

## 1. 담당 범위

프로젝트는 3계층 하드웨어 구조이며, 이 중 **상위 연산부의 판단·제어 로직**을 담당했습니다.

```
[ESP32-S3 + UWB]  V2X 송수신, UWB 거리·각도 연산          ← 타 담당
        ↓ 주변차량 정보 / 리더까지의 거리·각도
[Raspberry Pi 5]  적합도 판단, FSM 상태전이, 조향·속도 계산  ← 본 담당
        ↓ 목표 조향각(rad) / 목표 속도(m/s)
[STM32]           서보 PWM 변환, 엔코더 기반 모터 PID       ← 타 담당
```

**경계 원칙**: RPi는 "얼만큼 갈지"까지만 계산하고, PWM 듀티·모터 PID·아커만 기하 보정은
전혀 다루지 않습니다. 반대로 UWB 원시 신호 처리도 하지 않고 이미 계산된 물리값만 소비합니다.

## 3. 핵심 알고리즘

### 3.1 플래툰 적합도 판단 (설계문서 §5~§8)

주변 차량 중 누구와 결합할지 결정하는 4단계입니다.

**① 1차 선별** — 체크포인트 인접, 진행 방향 동일, 통신 범위 내

**② 절대조건** (하나라도 불만족 시 후보 제외)
```
C_join = C_P ∧ C_R ∧ C_H ∧ C_D ∧ C_S
        (참여허용, 경로중첩, 방향차, 거리, 안전상태)
```

**③ 적합도 점수** (가중합, 0~1)
```
S = 0.25·S_거리 + 0.35·S_경로중첩 + 0.20·S_속도 + 0.10·S_통신품질 + 0.10·S_방향
```

**④ 안정성 검증** — 순간적인 값으로 결합하지 않도록, **최근 5회 평가 중 4회 이상**
기준점수(0.70)를 넘어야 실제 결합 요청을 보냅니다.

### 3.2 상태 머신

```
SOLO_DRIVE ──> PLATOON_JOIN ──> PLATOON_MAINTAIN ──> PLATOON_EXIT ──┐
     ↑                                                              │
     └──────────────────────────────────────────────────────────────┘

SOLO_DRIVE 내부 매칭 파이프라인:
  V2X_SEARCH → EVALUATE → JOIN_REQUEST → (AWAIT_SETUP) → PLATOON_SETUP

PLATOON_JOIN 내부:
  JOIN_REQUESTED → LANE_ALIGN → GAP_CONTROL → STABILIZE
```

### 3.3 결합(JOIN) 절차

리더와 팔로워가 **반대 방향으로** 속도를 조절해 간격을 좁힙니다.

```
e_d = 현재거리 - 목표거리(0.8m)

리더:   v = 현재속도 - 0.3 × e_d    (감속해서 기다림)
팔로워: v = 현재속도 + 0.5 × e_d    (가속해서 따라붙음)
```

안전장치 2중: **접근속도 제한**(리더속도 +0.3m/s 이내), **변화량 제한**(주기당 0.05m/s).

완료 조건은 `같은 차선 ∧ 거리오차 ≤0.1m ∧ 속도오차 ≤0.1` 이 **1초 이상 유지**될 때입니다.

### 3.4 유지(MAINTAIN) 및 해제(EXIT)

유지 단계 목표속도 (설계문서 §20.2):
```
v_target = v_리더 + K_d(현재거리 - 목표거리) + K_v(v_리더 - v_자차)
```

해제는 **경로 기준**으로 시작합니다. 결합 시 저장해둔 공통 경로에서 남은 체크포인트가
1개 이하가 되면 EXIT에 진입해, 목적지에서 갑자기 흩어지지 않고 미리 간격을 벌립니다.

### 3.5 통신 절차 (설계문서 §10)

패킷 9종을 정의하고 양방향 처리를 모두 구현했습니다.

```
요청측                              수신측
  JOIN_REQUEST      ──────────────>
                                     자체 재검사 6단계
                                     (ID확인 → 참여허용 → 중복결합 →
                                      절대조건 → 자체적합도 → 승인/거절)
                    <────────────── JOIN_ACCEPT / JOIN_REJECT
  PLATOON_SETUP     ──────────────>  (플래툰 ID·역할 채택)
       ... 결합 진행 ...
  JOIN_COMPLETE     <─────────────>
```

거절 사유를 5종으로 구분했고(참여 비허용 / 이미 결합 중 / 절대조건 미달 / 적합도 미달 /
차량 미발견), 무응답 시 2초 타임아웃으로 매칭을 재시작합니다.

### 3.6 안전 처리

| 상황 | 대응 |
|---|---|
| 상대 차량 정보 1초 이상 두절 | 플래툰 해제 후 단독주행 복귀 |
| 라인 유실 (단독주행) | 0.3초 후 비상정지 |
| 라인 유실 (플래툰 중) | UWB로 앞차 추종하며 버팀 (뒤차 추돌 방지) |
| 전방 장애물 근접 | 비상정지 + 플래툰 전체에 EMERGENCY 전파 |
| STM32 failsafe 발동 | 동일 |

**초음파와 UWB의 교차 판정**이 이 부분의 핵심입니다. 플래툰 중에는 초음파에 리더가
항상 잡히므로 거리만으로는 장애물 판정이 불가능합니다. 그래서 다음 기준을 씁니다.

```
초음파 거리 < UWB 리더 거리 - 여유(0.15m)  →  둘 사이에 끼어든 물체
```

UWB는 V2X 장착 차량만, 초음파는 모든 물체를 보는 성질 차이를 이용한 것입니다.

## 4. 검증 방법과 결과

통신 하드웨어와 실차가 준비되기 전에 로직을 검증하기 위해, **메모리상의 가상 V2X 버스**
(`LoopbackBus`)를 만들어 두 대의 FSM을 한 프로세스에서 동시에 구동했습니다.

검증한 전체 시나리오:
```
매칭 → V1 결합요청 → V2 재검사 후 승인 → 역할 결정(V2=리더, V1=팔로워)
→ 거리 1.5m에서 0.8m로 수렴 → 양쪽 MAINTAIN 진입
→ 체크포인트 진행 → EXIT → 2.0m 분리 → 양쪽 SOLO_DRIVE 복귀
```

### 시뮬레이션으로 발견해 수정한 문제

**① 리더가 차선 정렬 단계에서 무한 대기**
정렬 판정이 "상대가 정면 ±10° 이내"였는데, 리더 입장에서 팔로워는 뒤쪽(약 180°)에
있어 조건을 영원히 만족할 수 없었습니다. 실차에서 발견했다면 원인 파악에 오래 걸렸을
문제입니다.

**② 라인 유실 후 정지/재출발 반복**
유실 타이머가 매 주기 초기화되어, "정지 → 옛 조향각으로 재출발 → 정지"를 반복했습니다.

**③ 조향 미분항 포화**
D 게인이 제어주기의 역수(50Hz면 50배)로 증폭되어 조향이 최대치로 튀었습니다.
현재는 P 제어만으로 시작하도록 기본값을 조정했습니다.

**④ 동일 물리량의 이중 경로**
FSM은 주변차량 목록의 거리를, 조향 계산은 별도 링크값을 참조하고 있었습니다. 두 값이
어긋나면 "FSM은 결합 완료로 판단하는데 조향은 다른 거리 기준으로 도는" 상황이 발생하므로,
단일 소스로 통합했습니다.

**⑤ 목표속도 계산 중복**
같은 제어 이득이 두 파일에 각각 존재해, 한쪽만 튜닝하면 판단과 제어가 어긋나는 구조였습니다.
속도는 FSM, 조향은 제어 모듈로 책임을 분리했습니다.

## 6. 미해결 항목

### 6.1 팀 결정이 필요한 사항

- **트랙 차선 수** — 단일 차선이면 차선 변경 로직이 불필요해집니다. 다차선이면 JOIN 중
  차선 변경 시 **옆 차선 점유를 판단할 센서가 현재 없습니다**(측면·후측방 센서 미탑재).
  설계문서 §24에도 "JOIN 중 차선 변경 실패"가 미해결로 남아 있는 항목입니다.
- **체크포인트 인식 방식** — 표지판/바닥 마커/주행거리 중 무엇으로 할지. 적합도 계산에서
  경로 중첩 점수가 가중치 0.35로 가장 크므로, 미정 상태에서는 결합 판단 정확도가 떨어집니다.
- **초음파 활용 범위** — 현재는 안전 감시용으로만 사용 중이며, 설계문서대로 MAINTAIN 단계의
  주 거리 센서로 쓸지 결정이 필요합니다.

### 6.2 타 모듈 연동 대기

- **라인트레이싱 연동** — 현재 스텁 상태이며, 조향이 전부 카메라 기반이므로 **이 연결이
  전체 시스템의 병목**입니다. 정규화된 오프셋(-1~+1)과 검출 여부(bool) 두 값만 있으면 됩니다.
- **STM32 프로토콜 교체** — STM32가 아직 구프로토콜(ASCII)을 사용 중이라 보드 간 통신
  테스트가 불가능합니다.
- **엔코더** — 팔로워 목표속도 계산식의 자차 실제 속도 항이 엔코더 값입니다.
  엔코더 구현이 플래툰 실차 시험의 선행 조건입니다.

### 6.3 실측 필요

`parameters.md`에 30여 개를 우선순위별로 정리했습니다. 가장 시급한 것은 축간거리,
최저·최고 주행속도, UWB 신뢰 측정거리, 거리별 RSSI 범위입니다.

## 8. 멘토님께 여쭙고 싶은 사항

1. **차선 변경 안전 확보** — 측면 센서 없이 JOIN 중 차선 변경을 안전하게 수행할 방법이
   있는지, 아니면 하드웨어 추가나 단일 차선 트랙으로 범위를 조정하는 것이 현실적인지

2. **결합 단계 제어 구조** — 현재 JOIN/EXIT의 속도식은 자차 현재속도를 기준으로 보정하는
   구조라 감쇠항이 없습니다. MAINTAIN처럼 상대속도를 기준점으로 하고 감쇠항을 넣는 구조로
   바꾸는 것이 나을지, 아니면 변화량 제한만으로 충분할지

3. **체크포인트 구현 방식** — 프로토타입 규모에서 현실적인 방법에 대한 조언
