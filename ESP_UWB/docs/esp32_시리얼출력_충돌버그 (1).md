# [긴급, 진단 수정본] v2x_targets가 매번 잘려서 수신 불가 — USB Serial/JTAG 콘솔 버퍼 크기 문제

**이 문서는 기존에 드렸던 "시리얼 출력 충돌" 진단을 정정하는 문서입니다.** 처음엔
디버그 로그와 JSON 출력이 서로 다른 태스크에서 부딪혀서 깨지는 것으로 봤는데,
**디버그 로그를 전부 꺼주신 뒤에도 증상이 똑같이 재현돼서** 원인을 다시 봤고,
훨씬 더 근본적이고 확실한 원인을 찾았습니다. 이번 진단은 실측 근거가 명확해서
높은 확신을 갖고 말씀드립니다.

---

## 1. 증상 (로그를 꺼도 재현됨)

`app_config.h`의 `APP_ENABLE_DEBUG_SERIAL_LOGS`를 `0`으로, `main.c`에
`esp_log_level_set("*", ESP_LOG_NONE)`을 추가해주신 빌드로 다시 테스트했는데도
Pi 쪽에서 `v2x_targets`를 여전히 한 번도 온전히 못 받았습니다. 이번엔 로그 텍스트가
전혀 안 섞여 있는데도 이렇게 나옵니다.

```
{"type":"v2x_targets","seq":3029,"timestamp_ms":606057,"self_veh{"type":"v2x_targets","seq":3165,"ti...
{"type":"v2x_targets","seq":0,"timestamp_ms":159,"self_vehicle_i{"type":"v2x_targets","seq":427,"tim...
```

**두 사례 모두 정확히 같은 지점(대략 64~70바이트)에서 잘립니다** — `"self_vehicle_id"`
필드 이름 중간(`self_veh` 근처)에서 항상 끊기고, 바로 다음 메시지의 시작이
줄바꿈 없이 이어붙습니다. 로그가 있을 때도, 없을 때도, seq 번호가 뭐든 항상
같은 바이트 위치에서 잘리는 걸 보면 — 이건 태스크끼리 우연히 부딪히는 레이스
컨디션이 아니라 **매번 100% 확정적으로 발생하는 구조적 한계**입니다.

---

## 2. 진짜 원인: USB Serial/JTAG 콘솔의 작은 버퍼

`sdkconfig`를 확인해보니 이 보드의 콘솔(표준출력)이 이렇게 설정돼 있습니다.

```
CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y
```

ESP32-S3 내장 **USB Serial/JTAG 주변장치**를 콘솔로 쓰고 있습니다 (Pi에서
`/dev/serial/by-id/`로 보면 "Espressif USB JTAG serial debug unit"이라는 이름으로
잡히는 게 이것입니다). 이 콘솔 드라이버는 원래 사람이 읽는 짧은 로그 한두 줄
찍는 용도로 설계된 경량 채널이라 **한 번에 내보낼 수 있는 버퍼가 USB Full-Speed
패킷 하나 크기(약 64바이트)로 매우 작습니다.**

`pi_serial_bridge_send_snapshot()`이 `printf()`로 만드는 `v2x_targets` JSON은
150~200바이트가 넘습니다. 이 버퍼 한계를 넘는 순간 나머지 내용이 잘리는 것으로
보이고, 그래서 항상 같은 위치(약 64~70바이트)에서 끊기는 겁니다.

**참고**: 이전에 디버그 로그(`printf`/`ESP_LOG`)를 껐던 수정은 방향 자체는
합리적이었지만, 이 버퍼 크기 문제와는 별개라 증상이 해결되지 않은 것으로
보입니다. 그 수정은 유지하셔도 되지만(불필요한 콘솔 트래픽은 줄여서 나쁠 것
없음), 이 문제의 해결책은 아닙니다.

---

## 3. 요청 드리는 수정 방향

콘솔(printf/표준출력)을 대용량 구조적 데이터(JSON) 전송 채널로 쓰는 것 자체가
설계상 맞지 않습니다. 아래 중 하나를 검토 부탁드립니다.

**옵션 A — 콘솔 API 대신 드라이버 API를 직접 호출 (변경 범위가 작음)**

`printf()` 대신 `usb_serial_jtag_write_bytes()`(`driver/usb_serial_jtag.h`)를
직접 호출하도록 `pi_serial_bridge_send_snapshot()`을 바꿉니다. 이 함수는 반환값으로
실제로 쓴 바이트 수를 알려주므로, **전체 문자열이 다 나갈 때까지 반복(loop) 호출**해서
버퍼 한계 때문에 중간에 잘리지 않게 만들 수 있습니다. JSON을 먼저
`snprintf()`로 하나의 버퍼에 완성한 뒤, 그 버퍼를 이 API로 나눠서(필요하면 여러
번 나눠) 전부 내보내는 방식이면 될 것 같습니다.

**옵션 B — Pi와의 통신을 콘솔과 완전히 분리 (더 근본적, 배선 필요)**

지금은 디버그 콘솔(USB-Serial-JTAG)과 Pi용 JSON 프로토콜이 물리적으로 같은
포트를 공유하고 있습니다. 별도의 하드웨어 UART(UART1 또는 UART2, 여유 GPIO
필요)를 새로 열어서 Pi와의 통신은 그쪽으로 옮기면, 표준 `uart_write_bytes()` API와
훨씬 큰 설정 가능한 링버퍼를 쓸 수 있어 이런 종류의 문제 자체가 사라집니다.
다만 물리적으로 Pi USB 포트 대신 GPIO-UART 배선(또는 USB-TTL 변환기)이 추가로
필요합니다.

둘 중 옵션 A가 지금 배선을 안 바꾸고 빠르게 시도해볼 수 있는 방법이라 먼저
시도해보시는 걸 추천드립니다.

---

## 4. 참고 — 이 문제와 무관하게 확인된 것들

- 인터페이스 문서와 Pi 구현(`v2x_node.py`)은 필드명, 열거값, 좌표계 계산식까지
  전부 문서 기준과 일치합니다. 이번 버그는 인터페이스 설계 문제가 아닙니다.
- Pi 쪽 파서는 깨진 줄을 만나면 조용히 버리고 다음 줄로 넘어가도록 방어 코드가
  있어서, 이 버그로 Pi 쪽이 죽거나 멈추지는 않습니다. 다만 유효한 데이터를
  하나도 못 받을 뿐입니다.
- 기존에 보내드린 `esp32_v2x_보강요청.md`(leader_vehicle_id 추가 요청,
  speed_mps 파이프라인 확인 요청)는 이 문제와 별개로 여전히 유효하지만,
  **이 버퍼 문제부터 먼저 해결되지 않으면 그 확인 자체가 불가능**합니다
  (JSON을 온전히 못 받으니 speed_mps 값도 확인할 수 없는 상태).
